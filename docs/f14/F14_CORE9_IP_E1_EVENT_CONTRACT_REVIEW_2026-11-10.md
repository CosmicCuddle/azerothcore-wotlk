## Integration blocker discovered in existing IP105 human-epoch candidate (read-only source audit)

The existing [IP105 DRAFT](https://github.com/CosmicCuddle/mod-individual-progression/pull/105) is **not directly safe to transplant as-is** into a Core9 map-worker callback:

1. Its [`CurrentHumanViewerEpoch`](https://github.com/CosmicCuddle/mod-individual-progression/blob/48c0e3613473b2b48cbea4830fdba68b968bdc74/src/IndividualProgressionF14LifecycleScript.cpp#L763-L774) calls `sIndividualProgression->isNormalAccount(const_cast<Player*>(viewer))` in the GUID callback hot path; [`isNormalAccount`](https://github.com/CosmicCuddle/mod-individual-progression/blob/48c0e3613473b2b48cbea4830fdba68b968bdc74/src/IndividualProgression.cpp#L541-L550) consults excluded/bot account classification through [`GetAccountMatch`](https://github.com/CosmicCuddle/mod-individual-progression/blob/48c0e3613473b2b48cbea4830fdba68b968bdc74/src/IndividualProgression.cpp#L481-L504). A cache miss performs blocking `AccountMgr::GetName` and `GetSecurity` **login DB queries**. `LoadAccountRegexes` clears this cache on reload. Therefore a future enabled per-creature callback **could block a map worker after cache misses/reload**. This is a source-path risk, NOT a measured performance incident and NOT a claim it happens with the macro currently OFF.
2. `isNormalAccount` excludes bot and excluded-regex accounts, but **does not itself check GM security**. The [IP105 `OnPlayerLogin` predicate](https://github.com/CosmicCuddle/mod-individual-progression/blob/48c0e3613473b2b48cbea4830fdba68b968bdc74/src/IndividualProgressionF14LifecycleScript.cpp#L786-L807) could therefore stamp an eligible non-headless **GM account** as a human viewer. An epoch stamp is **identity only**, never a Vanilla/non-GM rights entitlement. Independently verify GM account AND current GM mode in the later fail-visible policy.
3. **The purported epoch check is self-referential.** IP105 `CurrentHumanViewerEpoch` calls `stamp.Matches(currentGuid, stamp.loginEpoch)`, comparing the stored epoch to itself, not an independently verified current session generation. An old stamp with a plausible positive value is not an authenticated *current* viewer epoch. Future code must compare to an independently issued and lifecycle-managed current session token; zero/missing/stale/mismatched values fail visible.
4. **GM/classification freshness is not automatic.** The cached account name/GM/bot/excluded classification can remain stale after a mid-session security change; config reload clears its cache but does not by itself establish an atomic new map-safe epoch. Verify both GM-account authority **and** GM mode at the actual suppression decision, using an immutable published session/config-generation snapshot. Any missing/reloaded/security-changed input must revoke visibility eligibility and preserve restoration debt.
5. For a future integration, reuse the **unique epoch issuer and logout invalidation idea**, but move expensive account/source verification to a safe login/config publication path, bind classification and config-generation validity to an immutable current session stamp, and make the map-worker read **cache-only and fail visible** on absent/stale facts. Reload and logout must revoke stale stamps/consumers without a lock or reentrant Core callback. A separate reviewed IP runtime child and actual Core9 native build are required; do not quietly cherry-pick #105.

These five findings are **new integration review blockers** for this candidate, not defects claimed in its default-OFF current production behavior. The full E1/restore contract remains unimplemented.

### Explicit sequencing decision for proposal review

1. Define **per-map-worker-owned, per-map-instance E1 table(s)** and a *genuine* Core-owned batch context with a pass token and exact current viewer session. `UpdateData&` is a possible carrier, but the ABI is NOT chosen. The process-global token may have gaps; NEVER use a process-global "current token" lookup. Cross-map transfers invalidate the old map admission; do not run an old queued action on a new map. Same-viewer nested notifier requests must fail visible, not silently reuse an outer pass's context or corrupt `m_newVisible` while it is aliased by `VisibleNotifier`.
1a. At Begin, authenticate a **current** non-GM human viewer+era+config/security snapshot using an already published, cache-only session fact. Bind admission to the token for End and GUID sends. Do not insert GM/unknown/invalid viewers into the E1 table at all. If admission cannot be completed safely, record no E1 pass and keep stock visibility. A later GM-mode/security/reload change invalidates admission; never re-query Auth DB on the map worker.
2. Before any F14-positive decision, obtain IP's **immutable** verified actor and human-rights snapshot, authoritative creature incarnation and stage. If any fact is missing, expired, unsafe or circular, return **visible** and do not nominate. Original unrelated Core visibility denial still applies normally.
3. Only at a positively F14-caused, *actual* OUT transition emit a pre-send OUT nomination after proving #94 recordability; **withheld CREATE is not a packet and has no E1 candidate**. Independently at the normal, rights-safe, previously-owed restoration CREATE (row C′), nominate a **Create** candidate before the real CREATE block is built. Ordinary Core link/distance/phase changes never count as F14 suppression or owed restore.
4. Core must enforce **ordering as a real producer property**: the pass token reaches the per-target decision before SendToSelf sends, and there must be no path to nominate the token after the batch's send-call. E1's pure `Nominate` does not contain such a check: fabricating correct inputs after send could produce `Matched`. Later Core9 GUID callbacks may only Correlate an independently recorded pre-send F14 OUT or owed-restore CREATE; missing/crossed/stale evidence yields **NoCandidate/Unattributed** without ledger mutation.
5. For direct-route transitions, first require a separately reviewed packet-call evidence route at its actual packet sending functions. E1's existing batch-token API is not evidence for the direct path.
6. Any invalidated session, map transfer, new incarnation, range/phase/stealth loss, rights change, GM account/mode override, config OFF, capacity poison or unwind must **stop new F14 hiding** and retain original debt. Queue an owning-map **viewer-origin whole-sight batch rescan (not side-effect isolated from other viewers)** only after leaving every notifier pass and ScriptMgr callback; never call a visibility function with E1 locks held. `UpdateVisibilityForPlayer(false)` is the preferred route for reviewed packet provenance, not `UpdateObjectVisibility(true)`; it resends the whole viewer's sight range and its busy-map cost is unknown. Farsight (`m_seer != this`) and shared-vision observers require a distinct tested policy; fail visible on uncertainty, validate each actual human observer individually.
7. Establish a defensible ledger policy for lack of client ACK before *any* positive hiding is permitted. A successful source link and send call alone cannot close #94 obligations.
8. **Permanent E1 poison is a live consumer blocker.** With today's `Table<*,256>`, 257 distinct viewer Ends can poison the entire table and `ForgetViewer` will not unpoison it. Refuse unknown/GM or eligible-but-empty Ends at E1 (Core pass window still tracks closure); call `ForgetViewer` on old-map transfer and logout and cap nominated viewers at 255 per map shard with overflow fail-visible. The owning map worker alone mutates BOTH its E1 Table and #94 Protocol/Ledger shard; never hold either lock across Core callback. Preserve old-map debt across transfer/unload through a separately reviewed safe handoff/freeze or refuse positive concealment entirely; do not delete outstanding records. Specify backpressure, quiescence and diagnostics. On any poison, disable **positive F14 concealment** for that map, mark every owed pair for a viewer-origin whole-sight fail-visible batch recheck (not side-effect isolated from other viewers), and **do not reset, discard or clear the poisoned ledger** while any historic hidden pair might exist. A fresh generation requires independently proven quiescence, drained sessions, no outstanding restore debt and owner-approved pilot design; today's #94 ledger cannot clear debt from a send call or server relink. Thus positive F14 must stay disabled after any unreconciled restore until an independently reviewed completion policy exists. If proof is unavailable, remain disabled.
9. Treat any Core send call as **source-level packet-attempt evidence only**, not client receipt. The protocol may record direct or batched server relink and dispatch stages, but MUST NOT clear original #94 debt or assert client presentation on that basis. Owner-approved 3.3.5a two-human tests must establish practical recovery behavior before a positive pilot.

**Ownership:** One map update worker owns each per-map E1 table and matching #94 protocol/ledger shard. The Core pass-token source is process-global and monotonic but never serves as a session epoch. On transfer, old-map viewer state must be invalidated and debt preserved; a robust handoff is **not designed or tested yet**. The proposed max 255 admitted per-map viewers is conservative, **not** a capacity certification. Cross-thread access without a correct owner/handoff contract must keep positive F14 OFF.

**Client-proof blocker:** Since source does not provide an object-create/destroy client ACK, the current protocol cannot legitimately discharge debt on direct or batched sends. **Before any first positive hide**, the proposal keeps positive concealment OFF until CosmicCuddle approves an independently reviewed no-client-ACK debt-completion policy, failure recovery, and a bounded controlled client test design. Remaining debt after any later restore also keeps concealment OFF; a first hide is not an exception. A clean build alone is insufficient.

## Proposed L1 handoff ownership contract — 12 November 2026 (design only)

**Status:** review proposal, not a Core API, gameplay implementation, client ACK policy or permission to hide. Builds on the existing Core9 event contract and the actual Core14 pre-send guarded producer at `6dd1589b`; the latter does not implement this ownership transfer. Preserve #94/#85 and IP145 E1 model. The exact IP145 model (`65d0110e`) has no runtime consumer, and its `ObserveMapUnloaded` removes correlation candidates, not debt. Protocol `ObserveMapUnloaded` only revokes ledger pairs; it does not export/import or complete them. A map-owned protocol object must therefore never be destroyed solely because its map unloaded while records remain.

### Preferred conservative design for review: retain debt ownership, transfer only authorization to observe

- Use a process-lifetime, bounded, value-only retention owner for frozen/retiring shard records (or retain the original immutable shard allocation under an explicit lifetime owner). No raw Player/Creature/Map pointers cross map workers. Original viewer GUID + login epoch, creature map/instance + GUID + incarnation, reason and evidence remain exact. An old-map record is not rewritten into the new map's identity. **Do not implement this by copying only CopyExactPendingRestores:** that method intentionally omits active non-pending records and may report unattributed risk. First revoke/freeze at the source, then preserve the complete original shard, including poison/unattributed risk and any provisional reservations. The destination is fail-visible while retention ownership is unproven.
- Introduce a non-reused handoff generation distinct from login epoch and notifier pass token. At source transfer/unload: close positive admission, invalidate queued callbacks/pass tokens, revoke relevant records, seal the source shard only after the owning worker has stopped mutating it, publish a retention receipt under a single explicit owner. A receipt means **server memory ownership only**, not client restoration. Never block an owning map worker waiting for another worker or hold a lock across ScriptMgr, visibility, player/session, map removal or packet calls. No observer-side CREATE is issued to an old map from a new worker.
- Destination may perform ordinary Core visibility and independent current rights checks; it must not consume, clear or reinterpret old debt. Until R2 is decided and implemented, any unresolved retained debt disables positive F14 admission for the affected scope; if exact scope or retention fails, conservatively disable positive F14 globally. No stage grant, quest/loot rights alteration, or non-F14 visibility suppression. A new login epoch is not proof of client restoration of the old epoch.
- Map unload, logout, transfer cancellation, duplicate/out-of-order handoff, generation wrap, retention full, unknown incarnation or process shutdown: stop positive admission before losing information. Keep source allocation/records retained until ownership is established; failure to retain is a release blocker, not an eviction policy. No claim that a process restart or a new instance automatically resolves prior client presentation. Specify actual process-lifetime retention and shutdown limits before enabling anything.
- A map worker can resume positive admission only under a separately approved R2 policy with a proven bounded recovery path, authenticated E1/rights inputs, and reconciled retention ownership. This design deliberately does **not** solve R2 or permit the first hide. Source and destination may continue normal Core gameplay during F14 fail-visible mode; never force a player teleport/relog or kick to manufacture evidence.

### L1 independent review resolution — 12 November 2026 (supersedes conflicting proposal details above)

Review: [CS02-IP source findings](https://github.com/CosmicCuddle/Naxxramas-Server-Coordination/issues/11#issuecomment-6819520681). M1/M2 accepted as design blockers. The following are proposed requirements, not implemented behavior or an R2 approval.

1. **M1 — process-wide admission fence.** Every future positive initial OUT must use a process-wide sticky retained-debt/unknown-risk fence, not a fresh local ledger alone. Close the fence BEFORE any source handoff with debt, and before a potentially lossy teardown. A bare atomic load of the fence is insufficient to prove that no positive reservation races with closure: a serialized admission transaction must check the fence and reserve capacity atomically, and closure must exclude new admissions and account for ALL already-issued/in-flight reservations before any shard is sealed. No lock held across Core/script/packet/map operations. Existing reservations remain obligations; do not cancel by forgetting evidence. No reopening while R2 is unresolved. No new concealment authorization is granted by this design.
2. **M2 — map generation plus pass closure.** Never use E1 ForgetViewer as a transfer fence. Close the last admitted pass and preserve its tombstone, with a non-reused map ownership generation checked at every callback before touching E1 or protocol. Core's process-wide monotonic token source must remain shared across maps; neither token nor map ID replaces authenticated login epoch. A late callback to an old shard must be refused even if it has the same session and creature keys. Old-generation tombstones can be reclaimed only after a separately proven callback-quiescence and no-replay boundary; no automatic TTL.
3. **L2 — sealed retention.** A retained protocol must become immutable by construction (exclusive value ownership transferred to const storage, no outstanding mutable aliases, no callback with an old pointer). A const reference alone cannot revoke other mutable aliases. Preserve complete records and ledger, flags and counters, and provisional reservation state separately; discard only correlation candidates after fencing. Do not use CopyExactPendingRestores as a transfer format. Keep the existing epoch-shadowing behavior (I1) fail-closed; do not introduce an epoch-blind lookup.
4. **Bounded memory correction.** A cap plus one shard is NOT a proven bound with concurrent map updates or multiple already-active shards. Reserve a retention slot/byte budget *before* first positive admission for every shard that may carry debt; include all active, retiring and in-flight allocations in the global bound. When capacity or generation is uncertain, refuse new admission, never evict or overwrite. Retention storage lifetime must be independent of Map lifetime; map teardown must not be blocked indefinitely. A clean empty shard can be retired only after proving no in-flight reservation, no ledger/record, no sticky risk and quiescence. Until these invariants and allocation-failure handling are implemented, positive concealment stays OFF. Whole-shard retention is the initial safe option, not a claim of production memory feasibility.
