Its post-send GUID sidecar reports **all eligible uncontrolled creature CREATE/OUT blocks** it observed, including normal Core visibility changes, not only F14 actions. The F14 consumer's missing lifecycle macro and Core9 hook mismatch must **not** be hidden by defining an absent macro. ## Integration blocker discovered in existing IP105 human-epoch candidate (read-only source audit)

The existing [IP105 DRAFT](https://github.com/CosmicCuddle/mod-individual-progression/pull/105) is **not directly safe to transplant as-is** into a Core9 map-worker callback:

1. Its [`CurrentHumanViewerEpoch`](https://github.com/CosmicCuddle/mod-individual-progression/blob/48c0e3613473b2b48cbea4830fdba68b968bdc74/src/IndividualProgressionF14LifecycleScript.cpp#L763-L774) calls `sIndividualProgression->isNormalAccount(const_cast<Player*>(viewer))` in the GUID callback hot path; [`isNormalAccount`](https://github.com/CosmicCuddle/mod-individual-progression/blob/48c0e3613473b2b48cbea4830fdba68b968bdc74/src/IndividualProgression.cpp#L541-L550) consults excluded/bot account classification through [`GetAccountMatch`](https://github.com/CosmicCuddle/mod-individual-progression/blob/48c0e3613473b2b48cbea4830fdba68b968bdc74/src/IndividualProgression.cpp#L481-L504). A cache miss performs blocking `AccountMgr::GetName` and `GetSecurity` **login DB queries**. `LoadAccountRegexes` clears this cache on reload. Therefore a future enabled per-creature callback **could block a map worker after cache misses/reload**. This is a source-path risk, NOT a measured performance incident and NOT a claim it happens with the macro currently OFF.
2. `isNormalAccount` excludes bot and excluded-regex accounts, but **does not itself check GM security**. The [IP105 `OnPlayerLogin` predicate](https://github.com/CosmicCuddle/mod-individual-progression/blob/48c0e3613473b2b48cbea4830fdba68b968bdc74/src/IndividualProgressionF14LifecycleScript.cpp#L786-L807) could therefore stamp an eligible non-headless **GM account** as a human viewer. An epoch stamp is **identity only**, never a Vanilla/non-GM rights entitlement. Independently verify GM account AND current GM mode in the later fail-visible policy.
3. **The purported epoch check is self-referential.** IP105 `CurrentHumanViewerEpoch` calls `stamp.Matches(currentGuid, stamp.loginEpoch)`, comparing the stored epoch to itself, not an independently verified current session generation. An old stamp with a plausible positive value is not an authenticated *current* viewer epoch. Future code must compare to an independently issued and lifecycle-managed current session token; zero/missing/stale/mismatched values fail visible.
4. **GM/classification freshness is not automatic.** The cached account name/GM/bot/excluded classification can remain stale after a mid-session security change; config reload clears its cache but does not by itself establish an atomic new map-safe epoch. Verify both GM-account authority **and** GM mode at the actual suppression decision, using an immutable published session/config-generation snapshot. Any missing/reloaded/security-changed input must revoke visibility eligibility and preserve restoration debt.
5. For a future integration, reuse the **unique epoch issuer and logout invalidation idea**, but move expensive account/source verification to a safe login/config publication path, bind classification and config-generation validity to an immutable current session stamp, and make the map-worker read **cache-only and fail visible** on absent/stale facts. Reload and logout must revoke stale stamps/consumers without a lock or reentrant Core callback. A separate reviewed IP runtime child and actual Core9 native build are required; do not quietly cherry-pick #105.

These five findings are **new integration review blockers** for this candidate, not defects claimed in its default-OFF current production behavior. The full E1/restore contract remains unimplemented.

Core3.3.5a does not expose a reliable ordinary object-create/destroy receipt ACK. A callback cannot invent one.

### Explicit sequencing decision for proposal review

1. Define **per-map-worker-owned, per-map-instance E1 table(s)** and a *genuine* Core-owned batch context with a pass token and exact current viewer session. `UpdateData&` is a possible carrier, but the ABI is NOT chosen. The process-global token may have gaps; NEVER use a process-global "current token" lookup. Cross-map transfers invalidate the old map admission; do not run an old queued action on a new map. Same-viewer nested notifier requests must fail visible, not silently reuse an outer pass's context or corrupt `m_newVisible` while it is aliased by `VisibleNotifier`.
1a. At Begin, authenticate a **current** non-GM human viewer+era+config/security snapshot using an already published, cache-only session fact. Bind admission to the token for End and GUID sends. Do not insert GM/unknown/invalid viewers into the E1 table at all. If admission cannot be completed safely, record no E1 pass and keep stock visibility. A later GM-mode/security/reload change invalidates admission; never re-query Auth DB on the map worker.
2. Before any F14-positive decision, obtain IP's **immutable** verified actor and human-rights snapshot, authoritative creature incarnation and stage. If any fact is missing, expired, unsafe or circular, return **visible** and do not nominate. Original unrelated Core visibility denial still applies normally.
3. Only at a positively F14-caused, *actual* OUT transition emit a pre-send OUT nomination after proving #94 recordability; **withheld CREATE is not a packet and has no E1 candidate**. Independently at the normal, rights-safe, previously-owed restoration CREATE (row C′), nominate a **Create** candidate before the real CREATE block is built. Ordinary Core link/distance/phase changes never count as F14 suppression or owed restore.
4. Core must enforce **ordering as a real producer property**: the pass token reaches the per-target decision before SendToSelf sends, and there must be no path to nominate the token after the batch's send-call. E1's pure `Nominate` does not contain such a check: fabricating correct inputs after send could produce `Matched`. Later Core9 GUID callbacks may only Correlate an independently recorded pre-send F14 OUT or owed-restore CREATE; missing/crossed/stale evidence yields **NoCandidate/Unattributed** without ledger mutation.
5. For direct-route transitions, first require a separately reviewed packet-call evidence route at its actual packet sending functions. E1's existing batch-token API is not evidence for the direct path.
6. Any invalidated session, map transfer, new incarnation, range/phase/stealth loss, rights change, GM account/mode override, config OFF, capacity poison or unwind must **stop new F14 hiding** and retain original debt. Queue an owning-map **viewer-only batch rescan** only after leaving every notifier pass and ScriptMgr callback; never call a visibility function with E1 locks held. `UpdateVisibilityForPlayer(false)` is the preferred route for reviewed packet provenance, not `UpdateObjectVisibility(true)`; it resends the whole viewer's sight range and its busy-map cost is unknown. Farsight (`m_seer != this`) and shared-vision observers require a distinct tested policy; fail visible on uncertainty, validate each actual human observer individually.
7. Establish a defensible ledger policy for lack of client ACK before *any* positive hiding is permitted. A successful source link and send call alone cannot close #94 obligations.
8. **Permanent E1 poison is a live consumer blocker.** With today's `Table<*,256>`, 257 distinct viewer Ends can poison the entire table and `ForgetViewer` will not unpoison it. Refuse unknown/GM or eligible-but-empty Ends at E1 (Core pass window still tracks closure); call `ForgetViewer` on old-map transfer and logout and cap nominated viewers at 255 per map shard with overflow fail-visible. The owning map worker alone mutates BOTH its E1 Table and #94 Protocol/Ledger shard; never hold either lock across Core callback. Preserve old-map debt across transfer/unload through a separately reviewed safe handoff/freeze or refuse positive concealment entirely; do not delete outstanding records. Specify backpressure, quiescence and diagnostics. On any poison, disable **positive F14 concealment** for that map, mark every owed pair for a viewer-only fail-visible recheck, and **do not reset, discard or clear the poisoned ledger** while any historic hidden pair might exist. A fresh generation requires independently proven quiescence, drained sessions, no outstanding restore debt and owner-approved pilot design; today's #94 ledger cannot clear debt from a send call or server relink. Thus positive F14 must stay disabled after any unreconciled restore until an independently reviewed completion policy exists. If proof is unavailable, remain disabled.
9. Treat any Core send call as **source-level packet-attempt evidence only**, not client receipt. The protocol may record direct or batched server relink and dispatch stages, but MUST NOT clear original #94 debt or assert client presentation on that basis. Owner-approved 3.3.5a two-human tests must establish practical recovery behavior before a positive pilot.
