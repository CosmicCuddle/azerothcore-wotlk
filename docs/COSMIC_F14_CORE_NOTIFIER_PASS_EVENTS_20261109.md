Early return before notifier construction creates **no pass**. An absent/not-in-world/headless viewer creates **no pass**; a real WorldSession nonheadless viewer can get an audit pass including a GM who cannot be positively hidden by the separate IP policy. No global visible-player list, phase, movement, tap or gameplay writes.
2. **Token uniqueness:** `F14VisibilityPassTokenSource.h` contains a standard C++ `std::atomic<uint64_t>` CAS sequence instantiated **once** in `GridNotifiers.cpp`; tokens start at 1, are globally unique per Core process across map workers and only become zero on exhaustion, **never wrap/reuse** (including `UINT64_MAX`). It has no visitor Player pointer, character/creature GUID, authenticated login epoch or client receipt. Real consumer must separately validate full human viewer identity/login epoch and reject nested/reentrant scopes and stale/closed passes. The new script hooks are synchronous: any observer must never retain raw `Player*` afterward.
3. **Actual script broadcast only with explicit compilation:** `WorldObjectScript` and `ScriptMgr` add **three** gated no-op lifecycle events `OnF14ViewerVisibilityPassBegin(viewer,token)`, `OnF14ViewerVisibilityPassBatchSendAttempt(viewer,token)` and `OnF14ViewerVisibilityPassEnd(viewer,token)`. These are only wired by the guarded *actual* `VisibleNotifier` constructor/destructor and `SendToSelf()`. `BatchSendAttempt` is emitted **after** `i_player.SendDirectMessage(&packet)` when `i_data.HasData()` was true; it proves at most a **batch packet send-call attempt**, not which GUIDs were in the packet, visibility CREATE/OUT, per-client ordering, wire delivery or client ACK. `End` is separate even for a zero-data pass and must NEVER clear an existing previous-hidden creature restore debt merely because a pass closed or batch attempted.
